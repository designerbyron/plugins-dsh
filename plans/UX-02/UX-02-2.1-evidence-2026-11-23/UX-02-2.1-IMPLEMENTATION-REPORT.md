## 2. Decisiones técnicas autónomas (y por qué)

| # | Decisión | Alternativa descartada | Por qué |
|---|---|---|---|
| D1 | **Proyección pura separada** (`lib/workspaces-projection.mjs`) con la clave de ruta replicada y **prueba de paridad** contra `normalizeKey` | importar `roots-structure.mjs` desde el proyector | el alcance exige «sin fs, sin host»; la paridad medida evita que las dos reglas de `pathKey` se separen |
| D2 | **Identidad por `pathKey`**; el título nunca identifica | usar `id` del Host como clave de React | el `id` es del Host y puede faltar; la ruta es la identidad que el propio Host usa para resolver |
| D3 | **Raíz más específica gana**; una raíz *dentro* del workspace no asigna el contenedor | marcar `inside` en ambos sentidos | un workspace que contiene proyectos no es un proyecto; asignarlo sería falso y no reversible en la UI |
| D4 | **`relation:"none"` explícito** cuando no hay relación | `relation:null` | el caso T-W2-10 del alcance fija `relation:'none'`; el contrato lo declara como «ausencia representada» |
| D5 | **`status()` con 250 ms por elemento y 2000 ms de presupuesto total**; agotado → `unknown`/`budget` **sin perder filas** | truncar la lista por tiempo | truncar por tiempo haría la respuesta no determinista y ocultaría workspaces; el alcance pide `truncated` por número de filas |
| D6 | **`sessions.live: null`** cuando no hay servicio de sesiones, y `reason:"sessions-unavailable"` | devolver 0 | «no se pudo mirar» ≠ «cero vivas»; el propio proyecto ya fija esa regla (R16: `count:null`, nunca 0 inventado) |
| D7 | **Servicios por getter por petición** (`services` plano con getters en `index.js`, leído dentro del handler) | pasar `{list}` resuelto al crear el handler | el registro del Host puede no estar listo en `apply()`; congelar `null` convertiría una carrera de arranque en `source:'none'` permanente |
| D8 | **`stateReason` como clave aditiva** (`timeout`, `status-error`, `budget`, `no-status`, `unexpected-status`) | dejar `unknown` sin motivo | sin motivo, la UI no puede distinguir un disco lento de un fallo; es aditivo y no inventa datos del Host |
| D9 | **La ruta se responde antes de resolver el proyecto activo** | colgarla del `projectView` | el inventario del Host no depende de la selección; así funciona con perfil sin selección y con todo archivado |
| D10 | **Refresco al entrar + botón «Actualizar»**, sin polling | temporizador o eventos | el registro del Host no emite eventos de apertura/cierre (verificado en su código) |
| D11 | **Evidencia en `plugins-dhs-release/plans/UX-02/`** | escribirla en `plugins-dhs` | la excepción del propietario prohíbe modificar el otro worktree; `plans/` existe en ambos |

## 8. Limitaciones y riesgos residuales

| # | Limitación / riesgo | Impacto | Mitigación |
|---|---|---|---|
| L1 | El contrato del Host se leyó de su paquete (`dsh-workspace`, `dsh-session` dentro de `app.asar`), pero **no se ejecutó contra el Host vivo** (instalar el plugin está prohibido en este mandato) | el adaptador podría diferir en detalles no observables sin ejecución | el doble respeta el contrato leído (`status()` async, `list()` sync, `sessionIds` filtrados) y la prueba de cableado cubre el eslabón adaptador→API |
| L2 | `sessions.list()` devuelve sesiones vivas del store; si el Host no lo expone, `live` es `null` | no se distingue vivo/histórico | declarado en la UI y en el contrato (`noSessions`) |
| L3 | La relación workspace↔proyecto es **inferencia por ruta** (no hay vínculo persistido; D-UX-20 pendiente) | un cambio de ruta rompe la relación sin avisar | se publica como inferencia; no se persiste nada |
| L4 | Presupuesto de 2000 ms: en un volumen enorme de workspaces con discos lentos, filas quedarán `unknown`/`budget` | el usuario ve «sin comprobar» en algunas filas | motivo visible y botón Actualizar; nunca se pierden filas |
