# R16.1 — Conflicto de slot con `dsh-plugins-update` (diagnóstico y arreglo)

Estado: **arreglado en el entorno del usuario** (fuera del repositorio), pendiente de
reinicio para que se sirva. Fecha: 2026-11-09.

## 1. Síntoma exacto

En la consola del GUI real aparecía, una vez por ciclo de sincronización:

```
[client-store] subscriber failed: Error: keyed slot "plugins.bundle.config"
already has an entry for key "dsh-plugins-update" at priority 0
(registered by dsh-plugins-update) — register at a different priority to shadow it (lowest renders)
    at OI.register (index-BgUyXZcc.js:123:94406)
    at Proxy._register (client.js:1611:1)
    at A2.<anonymous> (client.js:1815:1)
    at registerBundleConfig (plugins/…:19027:15)
    at sync (client.js:1320:1)
```

No es el fallo del panel de LifeCode Skill Center (`uiWorkspace without inject`) ni
tiene relación con él: ése era del cliente de nuestro plugin y ya está corregido
(`uiWorkspaceService`, `client.js:1510`). Tampoco son nuestros
`[deepseek-account] account read failed`, `changes.summary 404`,
`plugins/events ERR_FAILED` ni `inspect query Slots.listSubTree: session/agent-busy`.

## 2. Causa raíz

`dsh-plugins-update` (dependencia `github:fengzhiyushu/dsh-plugins-update` del perfil
`desktop`) registra su tarjeta de ajustes así:

`~/.dsh/profiles/desktop/node_modules/dsh-plugins-update/lib/client.js:1122` (original)

```js
const registerBundleConfig = (form) => {
  ctx.slots.inject(
    "plugins.bundle.config",
    () => ctx.slots.register(
      { name: "plugins.bundle.config", key: "dsh-plugins-update" },
      () => import_react.default.createElement(RegistrySettingsCard, { form: form || getForm(), t, locale })
    )
  );
};
…
ctx.effect(
  () => ctx.configForms.whileServed(["dsh-plugins-update"], () => {
    const form = ctx.configForms.get("dsh-plugins-update");
    formInstance = form;
    registerBundleConfig(form);          // ← no devuelve el disposer
  }),
  "dsh-plugins-update: bundle settings card"
);
```

El contrato de `whileServed` que sirve el Host
(`@deepseek-ai/dsh-client-ui-settings/lib/client.js:1302-1334`, extraído a
`_audit/r16-conflict/`) dice literalmente:

> *«`register` runs once one of them is in the describe mirror, and its disposer runs
> when none is or when the returned disposer runs. […] `@returns` the disposer ending
> the watch and any live registration.»*

Y su implementación sólo puede retirar la inscripción si el callback devolvió el
disposer (`if (watched && off === void 0) off = register(served)`; al dejar de estar
servido: `off()`). Como el callback devuelve `undefined`, la inscripción **queda viva
para siempre**; cuando el namespace vuelve a servirse se registra otra vez la misma
clave y el mismo `priority` (0). El motor de slots del shell
(`dsh-web-frontend/dist/assets/index-BgUyXZcc.js`, regla extraída a
`_audit/r16-conflict/slot-register.txt`) rechaza duplicados en slots `keyed`:

```js
case "keyed": {
  if (e.key === void 0) throw new Error(`keyed slot "${e.name}" requires options.key`);
  const f = r.entries.find(h => h.options.key === e.key && (h.options.priority ?? 0) === n);
  if (f) throw new Error(`keyed slot "${e.name}" already has an entry for key "${e.key}" …`);
  break;
}
```

Registrar en otra prioridad (lo que sugiere el mensaje) **no** es la solución: dejaría
dos tarjetas vivas y la sombra crecería en cada ciclo. La solución correcta es devolver
el disposer, que es lo que exige el contrato.

## 4. Por qué esto es lo más robusto disponible

1. **Arregla la causa, no el síntoma**: cumple el contrato de `whileServed`; no hay
   prioridades artificiales ni supresión de errores.
2. **Idempotente y reversible**: el script detecta si ya está aplicado, guarda el
   original y `--revert` lo restaura byte a byte.
3. **Sobrevive a los reinicios** (lo que no sobrevive es una edición manual sin
   registrar).
4. **No daña el store de pnpm** (rename en vez de escritura in-place) y no toca
   `package.json`, `pnpm-lock.yaml` ni el resto del perfil.
5. **Falla cerrado**: si el paquete cambia de versión, la guarda impide aplicar el
   parche a ciegas; hay que revisar y actualizar el marcador.
6. **No entra en el manifiesto de commits del repo**: es un arreglo del entorno
   (`~/.dsh`), no código de LifeCode; queda documentado aquí y es reproducible.

Límite declarado: una reinstalación del paquete (`pnpm install` que lo restaure o una
actualización del plugin) revierte el arreglo. En ese caso, reaplicar con el script; lo
definitivo es que el autor devuelva el disposer (dos `return`) en su repositorio.
