**Fecha:** 2026-11-09 14:0x (America/Managua) · **Fase:** diagnóstico de sólo lectura, sin reiniciar DSH ni
tocar el bundle · **Autor:** Lead · **Directiva:** R16.2 (§1: no usar el estado del código en disco como

## 0. Conclusión en una línea

El 404 **no lo produce el router de DSH ni el registro del plugin**: lo produce el **despacho viejo**
(`lib/api.mjs` del commit HEAD `3b29510`, línea 152) que el proceso del Host cargó a las **10:58:52** y que
**no conoce** `/api/projects` ni `/api/inventory`. El cliente sí es el nuevo (lo sirve el Host desde disco,
con revisión nueva al recargar la página). Es un **estado mixto cliente-nuevo / backend-viejo**, no una ruta
mal registrada.

El módulo servidor del plugin se evalúa **una vez** al arrancar el Host; editar los ficheros no lo recarga.
El bundle cliente, en cambio, se sirve versionado por revisión y el manifiesto de arranque se **reconcilia
en cada carga de página** (`dsh-client-modules/lib/index.js`: `HASH_REVISION_LENGTH = 12`, «Versioned code is
immutable; mismatched revisions are rejected instead of serving newer bytes», y la reconciliación que
«reads the package manifest and the bundle metadata again»). Por eso una recarga de página puede traer un
cliente nuevo aunque el backend siga viejo.

## 6. Por qué el cliente sí es el nuevo

La captura del usuario (13:53) muestra textos que **no existen** en el cliente de HEAD (`HEAD:client.js`
288 560 B, 0 apariciones de `projects.refresh.legacy`) y sí en el actual (`client.js` 346 216 B, 15
apariciones): «Inventario heredado · El Host todavía no publica /api/projects…», once indicadores con
«sin comprobar», y el nuevo orden de pestañas. Además el dump de consola recogido antes (m01301) muestra
revisiones `…client.js&rev=7739324a1550` y `…&rev=db36631d92df` (12 hex = `HASH_REVISION_LENGTH`), es decir
revisiones **sucesivas** del cliente mientras el Host seguía arrancado.

La revisión exacta que sirve la página en este instante no es legible desde fuera (el HTML de arranque exige
el peer del navegador; `GET /` desde PowerShell devuelve 401). Lo que sí está probado: la página ejecuta un
cliente posterior a HEAD y el backend es HEAD.

## 7. Por qué NO es el router de DSH

1. El prefijo **sí está registrado**: la petición atraviesa `webServer.register({kind:'prefix', path:API_PREFIX})`
   (si no, el Host devolvería su propio 404/HTML, no el JSON del plugin).
2. El cuerpo del 404 es exactamente `notFound()` de `lib/api.mjs` («esa ruta no es de la API (<prefijo>)»).
3. `/api/workspaces`, servida por el **mismo** handler y el **mismo** registro, responde 200 y alimenta el
   inventario heredado del GUI.
4. El despacho por método funciona: `/api/state` (GET) sigue sirviendo el panel y `POST /api` de las acciones
   viejas no ha cambiado.

## 8. Causa raíz (defecto de producto, no de configuración)

1. **Ciclo de vida asimétrico**: el Host evalúa el módulo servidor del plugin al arrancar y no lo recarga al
   editar ficheros; el bundle cliente se sirve versionado y se reconcilia en cada carga de página.
2. **No hay contrato versionado ni handshake**: cliente y backend no pueden comprobar que son la misma
   versión. El cliente de R16.1 interpretó «404 en la ruta nueva» como «backend heredado» y activó el
   fallback `legacy` (`client.js:5118-5136`, `legacyReason:'route'`), enseñando un inventario heredado y dos
   banners rojos. Ese heurístico es exactamente lo que R16.2 §6 prohíbe: **un 404 no es señal de legacy**.
3. **Falta de diagnóstico honesto**: el panel no distingue «backend viejo identificado» de «backend
   incompatible/ausente/auth», ni muestra revisión de cliente/backend.

`compatible-r16` y el panel completo.

## 10. Lo que este diagnóstico NO afirma

- No afirma qué revisión exacta de `client.js` tiene cargada la página (no hay canal externo para leerla sin
  DevTools); sólo que es posterior a HEAD y que el backend es HEAD.
- No afirma que el mecanismo de actualización del cliente sea HMR en caliente: lo demostrado es que una
  carga de página reconcilia el manifiesto y sirve la revisión nueva. El renderer 1460 (12:51) es compatible
  con una recarga, y las ediciones del cliente posteriores a esa hora implican al menos otra recarga.
- No reinicia DSH, no alterna el bundle y no escribe en el almacén real: la prueba viva de `compatible-r16`
  queda para la aceptación humana documentada en `_audit/R16.2-ACCEPTANCE.md`.
