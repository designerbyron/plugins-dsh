## 0. Resumen ejecutivo

1. El paquete es **JSON de un solo fichero** con esquema `lifecode-skill-center/skill-bundle`,
   `schemaVersion: 1`, y una huella `checksum` que cubre **sólo cuatro campos** del contenido:
   `body`, `description`, `whenToUse`, `tags`. No cubre `skill.id`, `skill.version`, `title`,
   `references`, `origin`, `exportedAt` ni `note`.
2. Por tanto el checksum garantiza **integridad de transporte de esos cuatro campos**, no
   autenticidad ni identidad: cualquiera puede recomputarlo (no hay clave) y modificar `id`,
   `version` o las referencias sin que el lector lo note.
3. El ciclo real es: `export-skill` escribe `<root>/exports/<id>-<version>.json` con `flag:'wx'`
   (nunca reescribe) → el texto viaja a mano → `readBundle` valida tamaño, esquema, forma mínima y
   huella → la importación crea **una copia aislada** por la misma puerta de calidad que cualquier
   creación (`createSkill` → `evaluateSkill`): nunca toca la skill original ni las asignaciones.
4. En la instantánea S₂ la ronda ya tiene implementado lo esencial del diseño: `inspect-bundle`
   (sólo lectura, con vista previa y preflight medido), `import-bundle` con `confirmed:true`,
   `onConflict:'abort'|'copy'`, detección `already-imported` y procedencia en el bundle. **Lo que
   falta es que esa procedencia sea durable**: `normalizeSkill`/`normalizeState` la borran en la
   siguiente lectura+escritura (P0 abajo).
5. La suite de pruebas del plugin estaba **roja** en S₂ por dos pruebas que codificaban el
   comportamiento antiguo (medido: `node --test tests/distribute.test.mjs` ⇒ 2 fallos, ver §4.1).
6. Hay operaciones que **no se pueden garantizar** y el contrato debe decirlo: autenticidad del
   origen, confidencialidad del paquete, y que el cuerpo no contenga instrucciones (se tratan como
   datos, nunca como órdenes).

## 1. El contrato real del paquete

### 1.1 Envoltorio (`skill-bundle` v1)

| Campo | Tipo | ¿Obligatorio al leer? | ¿Validado por `readBundle`? | Notas |
|---|---|---|---|---|
| `schema` | string | sí (implícito) | sí, igualdad exacta con `BUNDLE_SCHEMA` | otro valor ⇒ `invalid-bundle` |
| `schemaVersion` | number | sí | sí, `Number(...) === 1` | coacciona `"1"`, `1.0`; otro ⇒ `unsupported-schema` |
| `exportedAt` | string ISO | no | **no** | se escribe pero nunca se lee |
| `checksum` | string hex64 | sí para pasar la huella | sí, se recalcula y compara | si falta o no coincide ⇒ `checksum-mismatch` |
| `note` | string | no | **no** | no viaja a la importación |
| `portable` | boolean | no | **no** | derivado de `warnings` al exportar |
| `warnings` | array | no | **no** | `[{path, reason:'absolute-path', detail}]` |
| `origin` | object | no | sólo normalizado, **no validado** | añadido en R16.4: `{app, skillId, version, exportedAt}` |
| `skill` | object | sí | parcialmente (objeto, `id` y `body` no vacíos) | ver 1.2 |

### 1.2 Contenido `skill`

| Campo | Tipo | ¿Se conserva al importar? | Notas |
|---|---|---|---|
| `id` | string | sí, como id base | validado sólo “no vacío”; **la regex del centro (`isSafeId`) no se aplica aquí**, se aplica después en `createSkill` |
| `title` | string | sí | el import usa `title || description || id` |
| `description` | string | sí | alimenta la huella y la puerta de calidad |
| `whenToUse` | string | sí | idem |
| `tags` | string[] | sí | idem |
| `references` | map o array `{path,content}` | sí (`copyReferences`) | **fuera de la huella**; se validan al importar con `invalidBundleReferences` (sólo `references/…`, sin `..` ni rutas absolutas) |
| `body` | string | sí | idem; sin máximo de longitud al crear |
| `version` | string | **no como versión** | se guarda como `origin.fromVersion`; la copia importada nace siempre `1.0.0` |
| `publishedAt` | string | **no** | se lee y se descarta |

### 1.3 Qué es (y qué no es) la huella

```js
// lib/distribute.mjs — bundleChecksum({ body, description, whenToUse, tags })
createHash('sha256')
  .update(JSON.stringify({
    body: text(body),
    description: text(description),
    whenToUse: text(whenToUse),
    tags: Array.isArray(tags) ? tags.map(String) : [],
  }), 'utf8')
  .digest('hex')
```

- **Cubre:** cuerpo, descripción, cuándo usarla y etiquetas, en ese orden y con esa normalización
  (`text()` recorta; no hay NFC/NFKC).
- **No cubre:** `skill.id`, `skill.title`, `skill.version`, `skill.publishedAt`, `skill.references`,
  `origin`, `exportedAt`, `note`, `portable`, `warnings`.
- **Implicación de seguridad:** la huella es un *checksum de contenido*, no una firma. Cualquiera
  puede editar `id`/`version`/`references` y **recalcular** la huella; y quien reciba un paquete
  manipulado no tiene forma de detectarlo si el emisor no está autenticado por otro canal. Además,
  cambiar un `reference` no invalida la huella: un texto adjunto puede alterarse sin romperla.
- **Lectura defensiva:** `readBundle` recalcula y compara (`checksum-mismatch`) y `importBundle`
  **vuelve a recalcular** antes de crear nada, así que la comprobación no depende de que el llamador
  use el lector correcto.

### 1.4 Límites y validaciones del lector (`readBundle`)

Orden real de comprobaciones (códigos exactos):

| # | Comprobación | Código si falla |
|---|---|---|
| 1 | entrada es string; `Buffer.byteLength(raw) <= 512*1024` | `bundle-too-large` |
| 2 | `JSON.parse` | `invalid-bundle` (“el paquete no es JSON”) |
| 3 | objeto no nulo | `invalid-bundle` |
| 4 | `schema === 'lifecode-skill-center/skill-bundle'` | `invalid-bundle` |
| 5 | `Number(schemaVersion) === 1` | `unsupported-schema` |
| 6 | `skill` objeto, `id` y `body` no vacíos | `invalid-bundle` |
| 7 | huella recalculada === declarada | `checksum-mismatch` |

No valida: `title`, `version` (formato), `references` (lo hace un paso posterior con
`invalidBundleReferences`), `publishedAt`, `origin`, ni el tamaño de cada referencia.

### 1.5 Escritura y ubicación

- Ruta: `<root>/exports/<skillId>-<version>.json`, con `root` = almacén del centro
  (`<DSH_HOME|~/.dsh>/lifecode-skill-center`, o `LIFECODE_SKILL_CENTER_ROOT`).
- `isSafeBundlePart` valida las partes del nombre: id `/^[a-z0-9][a-z0-9-]{0,63}$/`, versión
  `/^\d+\.\d+\.\d+$/`. Si no pasan, no hay ruta (`bundlePath` ⇒ `null`).
- Serialización `JSON.stringify(bundle, null, 2) + '\n'`; `writeFile(..., {flag:'wx'})`.
  Si el fichero existe ⇒ `bundle-exists` (“esa versión ya está exportada: el fichero no se
  reescribe”). Nunca sobrescribe.
- **No aplica el tope de 512 KiB al escribir**: un paquete grande se escribe y luego `readBundle` lo
  rechaza al leerlo (asimetría escritura/lectura, ver hueco G10).

## 2. Ciclo de vida real

### 2.1 Exportar (sólo una persona)

`POST /lifecode-skill-center/api/...` con `{action:'export-skill', skillId, version?, note?}` y
actor humano. La IA obtiene `approval-required` (“exportar una skill lo pide una persona”).
Escribe un derivado en `exports/`, **no toca el almacén**: el test lo comprueba byte a byte
(`distribute.test.mjs:127`, `assert.deepEqual(readFileSync(center.json), before)`).
Devuelve `{ok:true, exported:true, file, bytes, sha256, checksum, portable, warnings, json?}`.

### 2.2 El fichero viaja a mano

El paquete es el propio JSON: se copia, se pega o se sube. No hay transporte, ni firma, ni
sobre. `from` es **texto libre** que pone la interfaz.

### 2.3 Leer e importar: contrato base vs instantánea S₂

| Paso | Contrato base (272 líneas) | Instantánea S₂ (431+4065 líneas) |
|---|---|---|
| Vista previa | **no existe** | `inspect-bundle`: sólo lectura, devuelve `preview` con preflight real |
| Confirmación | **no existe**; al pulsar, se importa | exige `confirmed:true`; sin él `confirmation-required` (400) |
| Conflicto de id | **renombra en silencio** a `-copia`, `-copia-N` | `conflict` + `imported:false`; sólo con `onConflict:'copy'` explícito crea `-copia` |
| Repetición | no se detecta | `already-imported` por `(bundleChecksum, originalSkillId)` — **sólo si la procedencia es durable** (ver 2.5) |
| Preflight | **ninguno** (la acción no estaba en `ACTION_SOURCES` ni en `preflightActionOf`) | `actionPreflight({action:'import-bundle'})` → `create-skill`; `block` ⇒ 409 `preflight-blocked` sin escribir |
| Procedencia | `origin:{kind:'import', from, fromVersion, note}` | además `bundleChecksum`, `originalSkillId`, `originalVersion`, `importedAt` |

En S₂ el camino es explícito y en este orden: `actor==='human'` → `confirmed===true` →
`bundleTextOf` (string u objeto, serializado) → `readBundle` → `invalidBundleReferences` →
`loadState`+`canWrite` → `bundlePreviewOf` → `already-imported` / `conflict` (sin escribir) →
`actionPreflight` (bloquea antes de abrir el almacén para escribir) → `withState(importBundle)`.

### 2.4 Efecto en el almacén

`importBundle` **no escribe por su cuenta**: llama a `createSkill` (la misma puerta que cualquier
creación), así que pasan `normalizeReferences`, la evaluación con sus `blocksPublish` y la versión
inmutable `1.0.0`. Después sobrescribe el `origin` de la skill creada con la procedencia completa y
empuja un evento `skill-imported`. La original, sus versiones y las asignaciones de proyectos no se
tocan (hay pruebas explícitas: `distribute.test.mjs:110-111`).

### 2.5 Códigos y su HTTP real

`handleApiRequest` traduce el resultado con
`ACTION_HTTP_STATUS[code] ?? 200`: **un `ok:false` sin código mapeado sigue siendo HTTP 200**.
En S₂ están mapeados a 400: `confirmation-required`, `invalid-bundle`, `bundle-too-large`,
`unsupported-schema`, `checksum-mismatch`, `invalid-references`; a 409: `preflight-blocked`,
`evidence-incomplete`, `store-unreadable`; y `conflict` / `already-imported` viajan como
`{ok:true, imported:false}` (HTTP 200), que es correcto: no son fallos de transporte sino “la
persona debe decidir”. `approval-required`, `bundle-exists` y `store` **no** tienen estado propio
(200 con `ok:false`): la UI no puede distinguirlos por HTTP y debe mirar `code`.

## 3. Qué conserva y qué pierde un paquete

**Conserva (contenido de la versión):** `id` base, `title`, `description`, `whenToUse`, `tags`,
`body`, `references` (texto), el número de `version` sólo como dato de procedencia
(`origin.fromVersion`) y `publishedAt` sólo dentro del JSON.

**Pierde (y el contrato debe declararlo):**

| Dato | Por qué se pierde | Consecuencia |
|---|---|---|
| Identidad del centro de origen (uuid/instalación) | no existe en el esquema | dos centros con la misma skill son indistinguibles salvo por `from` (texto libre) |
| `origin` del centro de origen | el bundle sólo lleva `origin:{app,skillId,version,exportedAt}`; el `origin` de la skill no se exporta | no se puede auditar de qué instalación llegó |
| `projectId`, asignaciones y `enabled` | no se exportan (correcto: son del centro) | la copia no se activa en ningún proyecto (deseado) |
| Evaluación y `checksum` de la versión original | `createSkill` reevalúa desde cero | el paquete puede “pasar” con otra nota; el checksum de la versión es de 12 hex y se recalcula |
| `createdAt` de la versión | no se exporta | la copia nace con `now` |
| `status:'deprecated'` | no se exporta | una skill deprecada se importa como publicada |
| Historial de versiones | sólo viaja una versión | no hay merge de historial |
| `exportedAt`, `note`, `origin` del envoltorio al importar | se ignoran (salvo `origin.version` como respaldo) | sin fecha de exportación en el registro |
| Registro durable de importaciones | `state` no tiene colección de imports; se usa `origin` | ver P0: la procedencia se normaliza fuera |

### 5.2 `import-bundle` (implementado en S₂)

`POST` con `{action:'import-bundle', bundle, from?, note?, confirmed:true, onConflict?:'abort'|'copy'}`
(sólo humano). Sin `confirmed===true` ⇒ 400 `confirmation-required`.

| Situación | Resultado | ¿Escribe? |
|---|---|---|
| mismo paquete ya importado (`bundleChecksum`+`originalSkillId`) | 200 `{ok:true, imported:false, code:'already-imported', preview}` | no |
| id ocupado y `onConflict!=='copy'` | 200 `{ok:true, imported:false, code:'conflict', preview}` | no |
| preflight `block` | 409 `{ok:false, code:'preflight-blocked', findings, reasons, evidence}` | no |
| preflight `warn` | 200 `{ok:true, imported:true, …, findings}` | sí |
| éxito | 200 `{ok:true, imported:true, id, renamed, renamedFrom, origin, version:'1.0.0', checksum, bundleChecksum, portable, warnings, preview, saved}` | sí |

`onConflict:'copy'` devuelve `renamed:true` y `renamedFrom`; el nuevo id sale de la misma regla que
`importBundle` (`-copia`, `-copia-2`…).

### 5.3 Durabilidad de la procedencia (P0; propuesta)

El contrato de la ronda exige que `already-imported` y la auditoría **sobrevivan a un reinicio**.
Hoy no lo hacen porque `normalizeSkill` (y el mapa de eventos) son listas blancas. Opciones, de
menor a mayor coste:

1. **Extender la lista blanca de `origin`** en `normalizeSkill` con
   `bundleChecksum|originalSkillId|originalVersion|importedAt` (todos string|null). No cambia
   `SCHEMA_VERSION` (el objeto `origin` es aditivo y ya se normaliza), no requiere migración, y
   arregla G3/G5 de una vez. Es la propuesta preferida.
2. **Usar el libro durable que ya existe**: `recordOperation(state, id, {kind:'import-bundle',
   uuid, targetSha256:<bundleChecksum>, registeredAt, status:'registered'})` — `normalizeState`
   conserva esos campos (`state.mjs`, `operations`), así que serviría como registro de
   importaciones sin tocar el esquema. Ventaja: no depende de `origin`; desventaja: `operations`
   está pensado para identidad/manifiestos.
3. Añadir una colección raíz `imports`: exigiría `SCHEMA_VERSION` nuevo + migración + cambios en
   `normalizeState`. **No recomendado** para esta ronda.

Para el evento, o se amplía el mapeo de eventos (misma lista blanca) o se acepta que el diario
guarda el núcleo y que la auditoría vive en `origin`/`operations`. Lo que no se puede es escribir
campos que el propio normalizador borra.

### 5.4 Correcciones de contrato propuestas (P1/P2)

- **G9 – cubrir la identidad**: añadir al paquete `identityChecksum = sha256(id, title, version,
  references-normalizadas)` y verificar en `readBundle`/`importBundle`; mantiene `schemaVersion:1`
  como campo opcional (los paquetes viejos quedan “sin identidad verificable”, no inválidos).
- **G10 – tope al escribir**: `writeBundle` debe rechazar `Buffer.byteLength(contents) > 512*1024`
  con `bundle-too-large`, en vez de producir un fichero que el propio centro no puede leer.
- **G11 – alinear identificadores**: usar `isSafeId` también en `isSafeBundlePart`, o documentar
  que el id del paquete es más laxo y que `createSkill` puede rechazarlo después
  (`invalid-id`).
- **G14 – nombrar los bytes**: `preview.identity.bytes` → `canonicalBytes` (re-serialización) y
  añadir `textBytes` (lo que ocupa el texto recibido); el export ya devuelve los del fichero.
- **G13 – procedencia útil**: `from` debe describir el origen revisado (nombre del fichero +
  `origin.exportedAt` + checksum corto), no el literal `'panel'`.
- **G12 – estados**: exportar `status` y `publishedAt` en el bundle (aditivo) para no convertir una
  skill deprecada en publicada.

## 6. Seguridad: qué se puede y qué no se puede garantizar

**Se puede garantizar:**

- **No se sobrescribe nada**: `writeBundle` usa `wx`; la importación crea una copia y nunca toca la
  skill del id original ni las asignaciones.
- **No se escribe fuera de sitio**: `exports/` para paquetes; el almacén sólo por `withState`
  (candado + copia previa).
- **No se ejecuta nada**: el paquete es JSON; no hay `eval`, ni rutas ejecutables, ni plugins.
- **Límite de tamaño** antes de parsear (`Buffer.byteLength` > 512 KiB ⇒ rechazo).
- **Shape de referencias** acotado a `references/…` sin `..` ni absolutas
  (`invalidBundleReferences`); las rutas absolutas se **avisan** además como no portables.
- **Secretos**: la puerta de calidad (`evaluate.mjs`) bloquea PEM, tokens conocidos y asignaciones
  tipo `password: …`; el preview añade `possible-secret` como **aviso**.
- **Lectura sin efectos**: `inspect-bundle` no abre el almacén para escribir.

**No se puede garantizar (y la UI no debe insinuarlo):**

1. **Autenticidad**: no hay firma; la huella la recalcula cualquiera. Un paquete manipulado en
   `id`/`version`/`references` sigue siendo “válido”.
2. **Confidencialidad**: el JSON viaja en claro; los `references` pueden contener datos internos.
3. **Que el cuerpo no contenga instrucciones**: es *contenido*. Se evalúa como texto (calidad y
   secretos) y se muestra como datos; nunca se ejecutan sus frases.
4. **Detección exhaustiva de secretos**: las reglas son heurísticas (PEM, `sk-…`, `ghp_…`,
   `AKIA…`, `password:`…). Un secreto con otra forma pasa.
5. **Procedencia verificable**: `from` es texto libre; `origin.app` lo escribe el centro que
   exporta, no una autoridad.
6. **Deduplicación global**: `already-imported` es local y —hoy— no durable (G3).
7. **Que el paquete sea “seguro” en otro centro**: la copia se reevalúa, pero si el otro centro
   tiene otra política de calidad, el resultado puede diferir.

## 7. Correcciones a las premisas del encargo

1. “`importBundle` renombra en silencio”: **matiz** — renombraba sin preguntar, pero la UI sí
   avisaba *después* (`library.import.done` con el sufijo “(renombrada porque el id ya existía)”).
   El hueco real era la **ausencia de decisión previa**, no la ausencia de aviso.
2. “`schemaVersion` exacto”: se compara con `Number(...)`, así que `"1"` y `1.0` pasan. Sigue
   rechazando cualquier otra versión, pero no es una comparación estricta de tipo.
3. “El checksum no cubre `references`”: **confirmado** (ver 1.3); tampoco cubre `id`, `version`,
   `title` ni `publishedAt`.
4. “`export-skill` sin tope”: **confirmado** y es un hueco propio (G10), no estaba en la premisa.
5. “`import-bundle` devuelve HTTP 200 con errores”: **parcialmente corregido en S₂** (los códigos de
   paquete ya son 400); siguen en 200 `approval-required`, `bundle-exists` y `store`.
6. “`library.import.ready` existía sin uso”: era cierto en el contrato base; en S₂ la vista previa
   usa `portability.preview.*` y ese texto sigue definido sin uso (limpieza pendiente).
7. **Hallazgo no previsto y prioritario**: la procedencia escrita por la importación **no es
   durable** (G3). Es el hueco que más afecta a la promesa “sabemos de dónde vino y no lo
   reimportamos dos veces”.
