# R16.2 — Contrato de rutas y handshake de capacidades

Fecha: 2026-11-09 · Rama `feature/visual-operation-feedback` · Plugin `lifecode-skill-center`
Rutas de código relativas a `lifecode-skill-center/`. Este informe documenta lo implementado en R16.2;
las cifras de gate definitivas viven en `_audit/R16.2-GATES.md`.

## 1. Qué añade R16.2 y por qué

R16.1 estrenó `GET /api/projects` y `GET /api/inventory`, pero el panel no tenía forma de saber con qué
backend hablaba. El proceso DSH vivo conserva el módulo servidor evaluado al arrancar, mientras el bundle
cliente se sirve por revisión desde disco (ver `R16.2-LIFECYCLE.md`). Esa asimetría produjo un estado
mixto: cliente nuevo contra despacho viejo, 404 en las rutas nuevas y un fallback heredado que el cliente
activaba por heuristico. La corrección tiene dos piezas:

1. **Contrato versionado aditivo**: `API_CONTRACT_VERSION = 2` (`lib/api.mjs:89`), sin tocar `apiVersion`,
   que sigue siendo `1` (`lib/api.mjs:82`). Las rutas viejas y sus formas no cambian.
2. **Handshake** `GET /api/capabilities` (`lib/api.mjs:560-587`, `index.js:577-589`), servido sin
   credencial en el mismo prefijo y por el mismo registro que el resto de la API.

La regla que ordena todo el documento: **un 404 no prueba que el backend sea heredado**. El despacho viejo
responde 404 a rutas que no conoce, pero una entidad inexistente también produce 404. La compatibilidad se
decide sólo por el handshake, nunca por un código suelto.

## 2. Superficie HTTP

- Prefijo único: `API_PREFIX = '/lifecode-skill-center/api'` (`lib/api.mjs:112`), sin barra final.
  Medido sobre el harness vivo: una ruta con nombre casa por `path` o `path + '/'`, nunca por `path + 'x'`;
  registrada con barra final sólo respondía la base exacta (`lib/api.mjs:105-111`).
- `apiRouteOf(pathname)` (`lib/api.mjs:432-437`) devuelve `''` para la base exacta, la subruta sin barra
  para `API_PREFIX + '/'`, y `null` cuando el pathname no pertenece a la API. `null` ⇒ 404 `not-found`
  (`lib/api.mjs:620`); una subruta no reconocida también (`lib/api.mjs:729` para GET, `:747` para POST).
- Registro único: `registry.register({ kind: 'prefix', path: API_PREFIX, handler })` (`index.js:722`),
  dentro de `ctx.inject(['webServer'])` (`index.js:545-546`) y con retirada en el cleanup del efecto
  (`index.js:719-730`). Debe ser `handler`, no `resource`: un `resource` sólo contesta GET/HEAD y el
  servidor devuelve 405 a cualquier POST antes de mirar la ruta (`index.js:719-721`).
- El adaptador compone en cada petición los servicios del Host (`workspaces`, `skills`, `loader`,
  `sessions`) y mide la evidencia del preflight antes del despacho (`index.js:629-705`). El módulo puro
  no lee `ctx` ni `process.env` (`lib/api.mjs:592-595`).

## 3. `GET /api/capabilities` — el handshake

### 3.1 Orden de servicio

En `index.js` se sirve antes de la admisión y antes del 503 por falta de `connection`:

1. `health` es la primera superficie sin credencial (`index.js:562-568`).
2. `capabilities` es la segunda y última (`index.js:570-589`).
3. Un `Origin` ajeno se rechaza con 403 (`index.js:591-601`).
4. `admitRequest` aplica la puerta 401/403/503 (`index.js:603-609`).
5. Sólo después se lee el cuerpo y se toca el almacén (`index.js:611-622`).

El motivo está escrito en el código: si el handshake quedara detrás de la puerta, un 503/401 sería
indistinguible de un backend antiguo (`index.js:570-576`). En el despacho puro la rama de `capabilities`
va antes que `workspaces` y no depende de servicios (`lib/api.mjs:638-642`).

### 3.2 Payload exacto

`capabilitiesPayload({now, pluginVersion, implementation})` (`lib/api.mjs:560-587`):

```json
{ "ok": true, "kind": "capabilities",
  "plugin": { "id": "lifecode-skill-center", "version": "<package.json>" },
  "apiVersion": 1, "contractVersion": 2, "implementation": "r16.2",
  "contract": { "name": "lifecode-skill-center/api",
                "prefix": "/lifecode-skill-center/api",
                "minClientContract": 2, "maxClientContract": 2 },
  "capabilities": ["capabilities","projects","inventory","inspect-project",
                   "register-project","adopt-project","materialize-project",
                   "preflight","legacy-workspaces"],
  "routes": {
    "GET /api/capabilities": "capabilities",
    "GET /api/workspaces": "legacy-workspaces",
    "GET /api/inventory": "inventory",
    "GET /api/projects": "projects",
    "POST /api#inspect-project": "inspect-project",
    "POST /api#register-project": "register-project",
    "POST /api#adopt-project": "adopt-project",
    "POST /api#materialize-project": "materialize-project"
  },
  "generatedAt": "<ISO>" }
```

- `CAPABILITY_IDS` (`lib/api.mjs:92-102`) es la lista cerrada; las rutas POST se identifican por
  `POST /api#<action>`.
- `plugin.version` se lee de `package.json` con `createRequire`; si no se puede leer, viaja vacío y el
  handshake sigue respondiendo: la versión vacía es un dato honesto (`index.js:155-171`).
- `implementation: 'r16.2'` lo fija el adaptador (`index.js:584`); el valor por defecto del módulo es el
  mismo (`lib/api.mjs:567`).
- HEAD devuelve el mismo estado sin cuerpo (`lib/api.mjs:641` con el `head` del adaptador,
  `index.js:578-587`; prueba `tests/r16-routing.test.mjs:383`).

### 3.3 Lo que el handshake NO hace

No lee almacén, ni filesystem, ni servicios, ni devuelve rutas de disco, recuentos o datos del usuario
(`lib/api.mjs:552-558`; `index.js:573-576`). No autentica: es una superficie pública por diseño. No
identifica la revisión del cliente cargado; sólo declara qué implementa el backend que responde.

## 4. `contractVersion` en las respuestas de datos

Es aditivo, no cambia la forma existente:

- `GET /api/inventory` devuelve `contractVersion: 2` (`lib/api.mjs:1161`).
- `GET /api/projects` devuelve `contractVersion: 2` (`lib/api.mjs:1552`) y conserva `identity` para el
  panel viejo (`lib/api.mjs:1561-1562`).
- Ninguna respuesta nueva elimina campos previos; el cliente R16.1 sigue pudiendo leer las rutas.

## 5. Tabla de rutas

| Ruta | Métodos | Quién la compone | Admisión | Respuesta / notas |
|---|---|---|---|---|
| `/health` | GET/HEAD | `index.js:564-568` + `healthPayload` (`lib/api.mjs:419-421`) | **No** | `{ok, apiVersion, auth:'host'\|'unavailable'}`; sólo dice si el Host puede autenticar |
| `/capabilities` | GET/HEAD | `index.js:577-589`; `lib/api.mjs:640-642` | **No** | Handshake §3 |
| `/workspaces` | GET/HEAD | `index.js:629-636`; `lib/api.mjs:646-648` | Sí | 200 con `deprecated` (marca del contrato nuevo) o 503 `workspace-registry-unavailable` |
| `/inventory` | GET/HEAD | `index.js:637-651`; `lib/api.mjs:650-663` | Sí | 200 inventario + colisiones; 503 `skills-registry-unavailable`; 409 `store-unreadable` |
| `/projects` | GET/HEAD | `index.js:652-667`; `lib/api.mjs:665-679` | Sí | 200 proyecto/discovered/current/summary; 503 `workspace-registry-unavailable` |
| `/` y `/state` | GET/HEAD | `lib/api.mjs:729-730` | Sí | Snapshot del centro |
| `/insights` | GET/HEAD | `lib/api.mjs:680-698` | Sí | 409 si el almacén no se puede leer |
| `/knowledge` | GET/HEAD | `lib/api.mjs:699-708` | Sí | 200 legible / 409 ilegible, nunca cifras inventadas |
| `/doctor` | GET/HEAD | `lib/api.mjs:709` | Sí | Diagnóstico de instalación |
| `/diff`, `/skill` | GET/HEAD | `lib/api.mjs:710-728` | Sí | 400 sin parámetros; 404 entidad; 409 store |
| `/api` (POST) | POST | `lib/api.mjs:747-795` | Sí | Acciones `inspect-project`, `register-project`, `adopt-project`, `materialize-project`, catálogo e identidad; 403 `api-peer-restricted` para canal operador |
| `/origin-verify` | POST | `index.js:668-669` | Sí | Verificación de origen del contrato existente |

Un POST a una subruta distinta de `''`/`state` es 404 de ruta (`lib/api.mjs:747`), no 405: el 405 se
reserva a verbos no admitidos (`lib/api.mjs:733-735`).

## 6. Cómo distinguir los fallos

| HTTP | `code` | Dónde nace | Qué significa | Cómo se reconoce |
|---|---|---|---|---|
| 404 | `not-found` | `lib/api.mjs:479-481`, usado en `:620`, `:729`, `:747` | La **ruta** no existe en este backend | `message` contiene «esa ruta no es de la API» y el prefijo oficial |
| 404 | `project-not-found` | `ACTION_HTTP_STATUS` (`lib/api.mjs:125`) | La ruta existe, la **entidad** no | `action:'inspect-project'` con `projectId` inexistente |
| 404 | `skill-not-found` | `lib/api.mjs:722-727` | Entidad de catálogo inexistente | Sólo `GET /api/skill?id=…` |
| 401 | `unauthorized` | `admitRequest` (`index.js:282-292`) | Falta la credencial del Host | Ruta de datos, no `/health` ni `/capabilities` |
| 403 | `forbidden` | `admitRequest` (`index.js:282-292`) | El Host no confía en host/origen | Igual que 401, con rechazo 403 |
| 403 | `cross-origin` | `index.js:591-601` | `Origin` ajeno | Sólo peticiones directas con cabecera Origin |
| 503 | `auth-unavailable` | `admitRequest` (`index.js:255-301`) | El harness no ofrece `connection` | Cualquier ruta con admisión; el handshake sigue 200 |
| 503 | `workspace-registry-unavailable` | `lib/api.mjs:647`, `:804-812` | Falta el servicio de workspaces | `GET /workspaces` o `/projects` |
| 503 | `skills-registry-unavailable` | `lib/api.mjs` (payload de inventario) | Falta el catálogo de skills | `GET /inventory` |
| 405 | `method` | `lib/api.mjs:733-735` | Verbo no admitido en esa ruta | POST a rutas GET-only tras la puerta |
| 409 | `store-unreadable` | `unreadableResult` (`lib/api.mjs:444-459`) | El almacén no se puede leer; no se escribe | Cualquier lectura/escritura del centro |
| 409 | `preflight-blocked` / `evidence-incomplete` | `ACTION_HTTP_STATUS` (`lib/api.mjs:118-130`) | La operación no pasó la compuerta | Llevan `findings[]`/`sources[]` |
| 501 | `host-action-unsupported` | `ACTION_HTTP_STATUS` (`lib/api.mjs:126`) | El Host no expone la acción (`open-workspace`) | Sólo esa acción |
| 500 | `internal` | `index.js:706-708` | Fallo inesperado; se registra | Último recurso |

Regla práctica: **404 de ruta ≠ 404 de entidad**. El primero invalida la ruta; el segundo la confirma. Sólo
el handshake decide compatibilidad.

## 7. Reglas del cliente

### 7.1 Validación del handshake

`asCapabilitiesPayload` (`client.js:2127-2136`) exige `ok:true`, `apiVersion` ausente o `1`,
`contractVersion` numérico, `capabilities` array de strings y `plugin`/`contract` objetos si existen.
`compatible-r16` requiere además `contractVersion >= 2` **y** que la lista incluya `projects` e
`inventory` (`client.js:5347-5353`). Un 200 con forma inválida es `backend-incompatible`, no éxito.

### 7.2 La señal positiva de legacy

`asLegacyWorkspacesPayload` (`client.js:2138-2149`) no acepta un 404 como prueba. Exige las dos rutas
viejas con forma válida: `ok:true`, `workspaces[]` con `workspaceId`, `managed[]`, cada fila con
`title` o `path`, y **ausencia** de las claves nuevas: `deprecated` en el documento y `state` en cada
fila. Si aparece cualquiera de las dos, no es el backend heredado.

### 7.3 Los cinco estados

`loadCompat` (`client.js:5336-5384`):

| Estado | Condición | Efecto |
|---|---|---|
| `compatible-r16` | handshake válido, contrato ≥ 2, publica `projects` + `inventory` | Rutas nuevas y panel completo |
| `legacy-compatible` | `/capabilities` 404/405 **y** `/workspaces` con señal positiva | Aviso ámbar; no se consultan rutas nuevas |
| `backend-incompatible` | handshake inválido/versión menor, o 404/405 sin señal positiva | Banner rojo; operaciones R16 detenidas |
| `backend-unavailable` | red, 5xx o timeout | Banner rojo con reintento |
| `authentication-error` | 401/403 en handshake o en rutas de datos | Banner de autorización; sin recuentos |

En `compatible-r16`, un 401/403 en `/projects` o `/inventory` **reclasifica** el estado a
`authentication-error` (`client.js:5430-5446`): no se pinta «contrato roto» ni ceros. El
`CompatBanner` es el único sitio que explica el modo (`client.js:3061-3108`,
montado en `client.js:3505`) y en legacy no hay banners rojos de las rutas nuevas.

### 7.4 En modo no compatible no se llaman rutas nuevas

`loadProjects` corta antes de las peticiones si el modo no es `compatible-r16` (`client.js:5401-5424`):
deja `projectsData`/`inventoryData` en `null`, `complete:null`, `legacyReason:'handshake'` en legacy y
regresa. Las acciones R16 se deshabilitan con `compatActionsEnabled` (`client.js:2154-2156`) y el texto
`projects.compat.actions.blocked` (`client.js:224`). El reintento respeta el flag de ocupado
(`client.js:5390-5394`), y una prueba fija que no duplica peticiones (`tests/r16-ui.test.mjs:1350`).

## 9. Límites declarados

- El handshake **no** identifica la revisión exacta del cliente cargado: sin un canal externo (DevTools)
  el cliente no puede leer su propio hash de bundle. Por eso R16.2 tampoco afirma que la captura viva sea
  de una revisión concreta.
- `capabilities` es pública: no sirve para autorizar nada; la autorización sigue en `admitRequest`.
- No se ha probado el modo `legacy-compatible` contra el GUI vivo: se prueba con el módulo servidor
  exportado y con los renders `node:vm` (ver `R16.2-ACCEPTANCE.md`).
- No se ha modificado ninguna ruta existente; los códigos de error previos se conservan.
